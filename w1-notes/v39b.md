**Please fix:**
1. **This round's tunnel fix cuts off the end of the data** (`lib/forwarder.mjs:340` for CONNECT, `:262` for the inbound forward).
   - On upstream `close`, the forwarder now calls `destroy()` on the client socket. That throws away bytes still queued for a slow reader. The PR app then sees a clean FIN with the tail missing: the data it got is an exact prefix, with nothing corrupted, but it's short.
   - Reproduced independently on Node 22 (the forwarder image) and Node 24. With a slow reader of a close-delimited stream:

     | Client | Silently short |
     |---|---|
     | raw TCP | 2/20 |
     | Node `https` | 8/20 |
     | `curl` | 10/20 |

     With `Content-Length` framing it surfaces as an error instead: ECONNRESET in 4/20, curl exit 18 in 12/20. TLS doesn't save close-delimited bodies: Node's `https` and curl/SecureTransport accept EOF with no `close_notify`.
   - Neither handler existed at `a0fc244`, which lost nothing.
   - The inbound forward's real peer, the conductor's Node `http` client, never half-closes, and lost nothing. So the reviewer's browser is not affected, which is why one skeptic rated this low. But PR-pane egress over CONNECT is, and it can make base-vs-PR differences the PR didn't cause.
   - Fix: use `socket.destroySoon()` and `client.destroySoon()`, or `end()`.
     - Both gave 0 short runs out of 480 (`end()`) and 120 (`destroySoon()`).
     - Neither brings back round 1's leak: 300 idle tunnels under `ulimit -n 200` return to 0 connections.
     - `destroySoon()` is better: with `end()`, a PR app that keeps trickling bytes into a half-open tunnel holds it open.

     Add a test where an upstream sends 4 MiB and then closes, and a client paused for 500 ms then reads; assert every byte arrives, on both paths.
2. **The URL parsing added this round silently rewrites allowlist entries instead of throwing** (`canonicalHost`, `parseAllowlist` `:152`).
   - Every one of these threw at `a0fc244`, and now loads:

     | Entry | Loads as |
     |---|---|
     | `api.example.com@evil.org` | `evil.org` |
     | `*.example.com@evil.org` | `*.evil.org` |
     | `github.com/myorg` | all of `github.com` |
     | `registry.npmjs.org/@myscope` | all of `registry.npmjs.org` |
     | `api.example.com#prod`, `?x=1`, `user@example.com`, a tab | the bare host |
     | `93.184.216.0/24` | the single address `.0` |
   - Entries are operator config, so the PR can't write one, and no PR-reachable bypass follows.
   - But this contradicts judgment call A ("anything else throws: … a URL … a typo never opens more than was meant") and decision E ("fail closed"). An operator who writes a path-scoped entry now believes egress is limited to that path, while the untrusted PR app can reach the whole host. An entry can read as one host and admit another.
   - The test titled "…anything else throws" hides this: its only URL case throws because of the colon.
   - Fix: in `canonicalHost`, refuse input containing `@`, `/`, `?`, `#`, `\` or whitespace. Or require the parsed URL's username, password, search and hash to be empty and its pathname to be `/`. Add `api.example.com@evil.org`, `*.example.com@evil.org` and `github.com/myorg` to the must-throw list.
