**Independent review (orchestrator) of `0354973..5cf2b16` (the data-diff engine): REQUEST_CHANGES. Two high findings, both about PR-forced truncation**

One reviewer probed masking, denial of service and ways a PR can game the flags, and ran 45 hand mutants. Skeptics tried to refute each finding: both high findings held, and one medium was lowered to low.

**What holds:**
- **Trust:** `flagChanges` excuses a change only when `trusted === true`. `'trusted'`, `'advisory'`, `1` and `{}` are all refused. `trustOf` trusts only the `isolated` verdict, and `combine()` fails closed.
- **Flags compare rows and fields, not counts,** for keyed and multiset deletes, dropped columns and cleared fields. The "excuse by count only" mutant dies.
- **Odd values are handled:** Buffers, typed arrays, BigInt, invalid Dates, `__proto__` and `constructor` names, a 200,000-deep array and 5,000-deep nested secrets.
- **Tests:** 770/770 at `5cf2b16`, CI green. 42 of 45 mutants were killed.

**Please fix:**
1. **High: PR-forced truncation hides destructive changes completely** (`lib/data-diff.mjs:559`). In a truncated collection, `tally` uses only `max(0, countBefore − countAfter)`, and `updated` is always empty. A PR can force truncation in two ways:
   - Write more than `maxRows` rows. In the probe, the PR deletes all 50 users and inserts 10,001 junk rows. Result: `flags = []`, and divergence reports `pr-only` with `inserted: 9951, deleted: 0`.
   - Add a collection that sorts first, such as `aaa_padding`, and use up the shared 32 MB budget. `users` is then truncated, and a mass update of every role from `member` to `admin` gives `flags = []`. Without the padding, the same change is a red mass-change.

   Fix:
   - Don't let one collection starve the others. Give each collection a fair share, or budget the collections the seed snapshot already had before ones the PR added.
   - Emit a red flag (for example `unverified`) when the PR pane's diff of a collection is truncated and the base pane's is not, or when a truncated collection's count changed.
   - Correct README line 387.
   - Test both ways of forcing truncation.
2. **High: in a trusted session, PR-forced truncation turns another row's delete from red to amber** (`:515`). When only the PR side is truncated, `mine.items` is null, so the base's known keys are compared by count alone. Example:
   - the base deletes order 4 and the PR deletes order 3;
   - with padding forcing truncation, the result is `[orders, delete, amber]` and divergence `both`;
   - the keyed control gives red and `differs`.

   Excuse by count only when both sides are count-only, and apply the same rule in `divergence`.
3. **JSON held in a string is parsed only at a cell's top level** (`:198`). `body: '{"password":"hunter2"}'` inside an object, `['{"api_key":"sk-live-AAA"}']` in an array, and NDJSON log lines all show their secrets in clear. CHANGELOG:76 and judgment call E claim otherwise. Fix:
   - run `heldJson` on nested string values, bounded by depth and size;
   - for strings that look like JSON but don't parse, or are oversized, mask the whole string when a secret-looking key appears, or show only length and digest;
   - add tests.
4. **`SECRET_NAME` misses hyphenated names** (`:24`). For example, a stored headers object `{"X-Api-Key": "sk-live-…"}` shows the key in clear. Also missed:
   - `api-key`, `x-access-key`;
   - `database_uri`, `mongo_uri`, `connection_string`;
   - `encryption_key`, `master_key`;
   - `mnemonic`, `seed_phrase`, `recovery_codes`, `pinCode`.

   Use `[-_]?` throughout and add these names to the test list.
5. **The masker's per-(collection, field) cache never shrinks** (`:146`). Field names are PR-controlled. Five discarded snapshots with fresh names grew the retained heap from 75 MB to 234 MB. Cache per collection with a cap, or don't cache the `SECRET_NAME` test.

**Low:**
- **A mass-change is excused when only the row keys match** (`:568`). The PR can overwrite `role` or `email` on the same rows where the base changed `topic`, and still get amber. Divergence does show `differs`. Key update items by key plus the changed field names.
- **No per-cell size cap before parsing held JSON** (`:180`):
  - a 9.5 MB cell takes 1.3 s of synchronous work;
  - 25 MB of kept JSON retains 142 MB of heap;
  - diffing takes 3.2 s and divergence 2.5 s, both synchronous.

  Skip `heldJson` above about 256 KB and show length and digest only.
- **With `allowDeletes`, a duplicate key the PR adds turns updates into delete plus insert,** so cleared-field flags disappear (`:282`). Flag a lost key instead.
- **`classify` names only top-level fields** (`:155`), so `profile.email` shows in clear next to the same address's fingerprint. Apply the names inside JSON, or document the limit.
- **Nested secret digests aren't per field** (`:167`), so the same secret is equal across fields and tables. The README says a secret's digest belongs to its field. Include the collection, field and path.
- **`Set` and `Map` values serialize to `{}`** (`:128`), so changes to them are invisible. DynamoDB's `lib-dynamodb` returns `Set`s. Convert them, or record a problem.
- **Three mutants survive.** Add tests that:
  - a soft-delete field re-set from one value to another is not a delete;
  - the same PII value in two tables has an equal fingerprint;
  - short or numeric nested secrets, such as `{pin: 1234}`, are masked.

**Nits:**
- **README:427 says every flag is red when untrusted, but `cleared` stays amber.** Reword it.
- **`Object.keys(given)` sits outside the `try`** (`:238`).
- **The cache key uses NUL as a separator,** so names containing NUL can collide (`:150`). Use a nested `Map`.
