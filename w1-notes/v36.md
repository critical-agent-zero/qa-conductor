One reviewer read the whole diff, ran four probes and 25 hand mutants. Skeptics could not refute any finding and lowered the one high finding to medium.

**What holds:**
- **Nothing reaches GitHub:** `verdict.mjs` and `github.mjs` are untouched.
- **Nothing leaks in events or logs:** capture events carry only `{kind, pane, phase, ok}` and a time stamp. Inspector errors go only to `view().errors`, and nothing in the capture code logs.
- **Access:** both routes sit behind the capability, same-origin and harness-host checks, and both answer `no-store`.
- **Trust** follows the current session's isolation verdict.
- **Snapshots:** concurrent snapshots share one run, and a snapshot that races a teardown answers 409.
- **Closing:** probes close at teardown and when a boot fails or is superseded.
- **Demo:** the PR's deletion of saved carts is flagged red as `pr-only`.
- **Tests:** 789/789 at `0991ab1`, CI green. 23 of 25 mutants were killed, including every trust, capability and probe-closing mutant.

**Please fix:**
1. **A failed PR-pane ready snapshot permanently hides the PR's boot changes, and the next successful snapshot erases the error** (`lib/data-capture.mjs:132`). `ready()` drops the seeded snapshot even for a pane whose ready read failed, and `take()` clears `errors[pane]` on any success. Example:
   - the PR's migration deletes every saved cart, then the PR pane's ready read times out;
   - one **Snapshot now** later, the view shows `errors {null, null}`, `boot.pr null`, `boot.flags []` and `session.flags []`;
   - a **Re-baseline** gives the same.

   Fix:
   - keep the seeded snapshot until that pane has a baseline, and compute the boot delta when one arrives;
   - keep errors per span, so a later success doesn't erase the reason;
   - have `span()` say `complete: false` instead of `flags: []` when a pane has no data;
   - add a test.
2. **A failed Snapshot now keeps the pane's old snapshot but stamps the new time** (`:156`). The view then compares stale data as current: PR `saved_carts` shows `same`, flags are `[]`, and only `errors.pr` hints otherwise. A partial **Re-baseline** leaves mismatched baselines under one `baselineAt`, and after the next success it shows a false red `pr-only` delete. Fix: on a failed read, set that pane's snapshot to null, or keep per-pane times and compare only snapshots from the same run. Test one-pane failures for both **Snapshot now** and **Re-baseline**.
3. **`limits.timeoutMs` only stops the wait** (`:85`). The timed-out `open()` or `snapshot()` is never signalled, and each retry starts another. Three timed-out snapshots left six probe reads running until `close()`. Give each call a signal that aborts at the timeout (`AbortSignal.any([parent, AbortSignal.timeout(ms)])`), and document it.
4. **`GET /api/data` is far larger than the 32 MB bound in judgment call E,** and every read rebuilds it (`lib/server.mjs:965`).
   - Example: 4 tables of 10,000 rows, rewritten at boot and again during the session, give 275 MB of JSON. `view()` takes 510 ms and `JSON.stringify` 1.3 s, both on the event loop the pane proxies share.
   - Every GET and every waiter that shares one snapshot run recomputes and re-serializes it.

   Fix:
   - cache the serialized view, keyed on the baseline time, the compared time and trust;
   - cap or page the rows a diff sends;
   - limit concurrent answers;
   - state the real worst case.

**Low:**
- **Each Snapshot now or Re-baseline adds two `capture` events to `progressLog`** (`server.mjs:410`). Every new stream client replays them until the next boot. Don't broadcast those phases, or cap the log.
- **A hanging inspector can add up to 150 s to a boot,** not 30 s: 2 × (30 + 30) + 30. Document it, or give one budget per boot.
- **`runBoot` doesn't await `endCapture()`** (`:613`), although the README says the next boot closes the probes first. Await it.
