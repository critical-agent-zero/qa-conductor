## 1. Goal and scope

**Goal.** One canonical package that:
1. carries every #307 defence the frozen copy has, adapted so the local consumers (self-QA, the demo, agent-identity) keep working with no new config;
2. owns its tailnet endpoints as the spec designs.

When it ships, homefree can delete its frozen copy and its apply-script mounts at Stage 2 A1.

**In scope (this repo):**
- **#329 parity:**
  - the harness API guard and the pane request guard;
  - harness and pane framing, and the `data-harness` bridge;
  - `cfg.harnessOrigin`;
  - the identity gate, and a loopback-only bind in tailscale mode;
  - `QA_GHCR_TOKEN` / `packagesToken`;
  - `rel="noopener"` on the harness's "Open in new tab" links.
- **Beyond #329:** the harness API answers browsers only at the harness origin's host and port (D10).
- **Exposure:**
  - `lib/exposure.mjs`: `mountsFor`, `reconcileExposure`, `runExpose`;
  - `lib/adapters/exposure-tailscale.mjs`;
  - the reconcile loop and `GET /api/exposure`;
  - the `qa-conductor-expose` bin, an operator and debug tool that no deploy runs (D14).
- **Self-QA and the demo:** the changes nested framing forces, an always-ungated demo, and self-QA wiring the adapter on a tailnet layout.
- **Publishing (UP):** the package becomes publishable to npm, and a tag-triggered workflow stages each release, which a maintainer approves on npmjs.com (D13).
- **Release:** the README, a CHANGELOG with migration notes, version 0.3.0, and tag `v0.3.0`, which stages 0.3.0, the first npm version.

**Out of scope:**
- other exposure adapters (Caddy, Cloudflare);
- per-login roles, and identities for tagged devices;
- removing serve handlers (D11);
- a plain `npm publish` from anywhere: only the tag workflow stages versions (D13);
- homefree values in the core: branding, the docker label, the postgres identity, `packageName` and `rcTagPattern` stay values the platform passes.

**Stays in homefree for A1 (section 4):**
- `config-homefree.mjs` and `compose-homefree.mjs`;
- the `homefree-qa-conductor` image (its Dockerfile and the CI job that pushes it to GHCR), which the compose file runs in place of the bind-mounted source (Q2);
- the compose file's tailscale CLI and socket mounts (D14);
- the apply script, reworked onto the image: it keeps #307's preflight and fail-closed checks, and drops its `tailscale serve` lines (D14);
- the Apply QA Conductor Env workflow (`.github/workflows/apply-qa-env.yml`), whose box check and preflight read paths that A1 deletes;
- the RUNBOOK and `P/qa-conductor/test/access-guard.test.mjs`.

So of the exposure plan, Tasks 2, 6 and 9–12 are not upstream work, and Task 8 is only partly (section 4):
- Task 2 is obsolete: #329 made `QA_ALLOWED_LOGINS` required, supplied by env-sync, instead of a committed default.
- Task 6 is replaced by a server-level wrap (D10).

## 2. Decisions

### D1. Two exposure modes; the default follows every address the conductor answers to

**Choice.**
- `QA_EXPOSURE` is `none` or `tailscale`. Any other value throws.
- Unset, it is `none` only when all of these are loopback (`127.0.0.0/8`, `::1`, `localhost`), and `tailscale` otherwise:
  - the harness origin, resolved at start as U1's `harnessOrigin()` would: `cfg.harnessOrigin ?? defaultHarnessOrigin({ publicHost, host, port: cfg.ports.harness })`;
  - both pane origins; a missing or unparseable one counts as non-loopback;
  - `publicHost` and every `allowedHosts` entry, since both widen the Host allowlist;
  - the bind host, `cfg.host ?? '127.0.0.1'`.
- A `null` harness origin adds nothing. It arises only without a public host, in one of two ways:
  - from a loopback bind on port 0, where the origin is derived per request from that loopback port;
  - from a non-loopback bind, which counts on its own.
- One exported resolver serves both `loadConfig` and a hand-built `cfg` that has no `exposure`:
  - `defaultExposure({ harnessOrigin, paneOrigins, publicHost, allowedHosts, host }) → { mode, because }`, in `lib/config.mjs`;
  - `because` names the first non-loopback input, for the error messages (for example `QA_PUBLIC_HOST=w.ts.net`), or is `null`.
- The mode is fixed at start. A `cfg` whose non-loopback origins are assigned after start must set `exposure` itself. `README.md:207` allows a late `paneOrigins`, and gains that sentence.
- `tailscale` turns the identity gate on (D2) and makes the bind and allowlist checks fatal (D3). `none` is 0.2.1's behaviour.
- The demo always sets `exposure: 'none'` (U2). It binds loopback, and when it is nested in self-QA it sits behind the outer conductor's gate.

**Alternatives.**
- **Default `tailscale`** (exposure plan Task 1, `env.QA_EXPOSURE || 'tailscale'`). It 403s every request in self-QA, the demo and agent-identity, which never carry the header.
- **Default `none`.** A tailnet layout stays ungated unless someone opts in, which is the #307 failure.
- **Keying on `QA_PUBLIC_HOST` alone.** It misses explicit https pane origins set without a public host.
- **Keying on the three origins alone** (this plan's first draft). Two layouts stay ungated:
  - a hand-built `cfg` with a public host and loopback pane origins, whose harness origin is derived from that host;
  - `QA_ALLOWED_HOSTS=box.ts.net` behind a hand-made `tailscale serve`. Any tailnet device can curl the API, since non-browser clients pass the API guard.
- **In `none` mode, a 403 for any request that carries `Tailscale-User-Login`.** It would catch only a deliberate `QA_EXPOSURE=none` behind serve, and tagged devices send no header.

**Why.** The gate should be on exactly when the conductor is meant to be reached from another machine, and the addresses it binds and answers to say that.
- All three local consumers resolve to `none` with no config change:
  - self-QA (`qa/self.mjs:79-85`) and agent-identity (`AI/src/config.ts:10-14`) default only loopback pane origins, and set no public host, allowed host or bind host;
  - the demo sets `none` explicitly.
- homefree resolves to `tailscale`, and commits it anyway (section 4).
- A 0.2 consumer with a non-loopback layout behind some other front door gets a startup error that names `QA_EXPOSURE=none`, not a silent behaviour change. That includes a `QA_BIND_HOST=0.0.0.0` bind.

### D2. The gate and the adapter are separate switches

**Choice.**
- `cfg.exposure === 'tailscale'` means "fronted by `tailscale serve` on this host": the gate is on for all three servers.
- `adapters.exposure` being present means "the conductor manages its own mounts": the reconcile loop runs.
- Tailscale mode without an adapter is valid. It is homefree today, with mounts set by the apply script. The conductor logs `[qa] exposure: tailscale serve mounts are managed outside the conductor` and reports `managed: false`.
- An adapter in mode `none` makes `startConductor` throw.
- The core never constructs the adapter. Platforms inject it like the other five seams.

**Alternatives.**
- **The spec ties the two together:** `QA_EXPOSURE=none` disables the adapter and the gate at once.
- **The exposure plan's Task 8** builds the adapter in the platform whenever the mode is tailscale.
- **A core that constructs the adapter itself** would rewrite a developer's own `tailscale serve` config whenever their addresses resolve to tailscale mode.

**Why.** homefree can adopt the gate before it trusts the adapter. And an ungated conductor can never publish itself.

**Limit.** The gate trusts `Tailscale-User-Login` from anything that can reach loopback on this host.
- With provisioner-process, the pane processes run PR code on the same host, as the same user. They can reach loopback and send any login they like.
- So in tailscale mode the gate does not protect against PR code. Only build-worktree's trust gate does.
- U4's tailnet self-QA is exactly this layout.
- Container panes that are not on the host network can't reach the host's loopback.
- U2's README bullet says all this.

### D3. Where the fail-closed checks live

| Condition | `loadConfig` | `startConductor` | reconcile / CLI |
|---|---|---|---|
| unknown `QA_EXPOSURE` / `cfg.exposure` | throws | throws | — |
| tailscale mode and a non-loopback `QA_BIND_HOST` / `cfg.host`. A non-loopback bind alone makes the default tailscale (D1), so `0.0.0.0` needs an explicit `none`. | throws | throws | — |
| tailscale mode, empty allowlist | throws | logs an error; every request is refused | — |
| `adapters.exposure` in mode `none` | — | throws | — |
| a harness, pane or frame-ancestor value that is not an http(s) origin | throws | throws (`harnessOrigin`, `frameAncestors`) | — |
| an `http:` harness or pane origin whose host isn't loopback (browsers send it no `Sec-Fetch-*`, so the guards would take other pages for curl; added in U1 review) | throws | throws, for `cfg.harnessOrigin` and each pane origin set at start | — |
| the harness origin equals a pane origin | throws | throws, comparing the start-time harness origin (D1) with each pane origin set at start | — |
| the two pane origins are equal | throws | — (the demo's placeholders are equal) | — |
| a missing or unparseable pane origin on a hand-built `cfg` | — | counts as non-loopback (D1) | `mountsFor` throws; recorded and logged; the CLI exits 2 |
| no harness origin can be derived (non-loopback bind, no public host) | throws | logs an error; the panes can be framed only by themselves, and the mirror is off | — |
| `exposureIntervalMinutes` not finite, ≤ 0, or > 35791 | throws | throws | — |
| mount layout: an http origin, two mounts on one port, listen port 0 | — | — | recorded and logged; the CLI exits 2 |
| adapter or CLI failure | — | — | recorded; never crashes; the CLI exits 1 |

**Why.**
- Config errors fail at load time, where homefree's apply-script preflight already catches a config that doesn't load.
- `startConductor` throws only on what would otherwise fail open.
  - An empty allowlist already fails closed, so it only logs, as #329 does (`F/lib/server.mjs:187-188`).
  - A harness origin equal to a pane origin is fail-open on a hand-built `cfg` too, so `startConductor` checks it as well.
  - Pane against pane is not checked there: the demo's placeholders (`demo/index.mjs:37`) are equal until its proxies listen. A loopback-derived harness origin collides with those placeholders only on port 80.
- Exposure never takes the conductor down (spec §2).
- A harness that shares an origin with a pane would be same-origin with PR code, which could then drive the harness API. So the three origins must differ.
- 35791 minutes is the largest whole number of minutes under `setInterval`'s 2³¹−1 ms limit. Above it, Node fires every 1 ms, and the loop would run `tailscale serve status` back to back.

### D4. One harness origin, derived; the harness path is fixed at `/qa`

**Choice.** `cfg.harnessOrigin` is a bare origin, resolved in this order:
1. `QA_HARNESS_ORIGIN`, if set: validated as http(s), with any path dropped (#329's `webOrigin`, `F/lib/config.mjs:36-44`).
2. Otherwise, if `QA_PUBLIC_HOST` is set: `https://<QA_PUBLIC_HOST>:8444`.
3. Otherwise, if the bind is loopback and the port is fixed: `http://<QA_BIND_HOST>:<QA_HARNESS_PORT>`, with brackets for IPv6.
4. Otherwise, `loadConfig` throws `QA_HARNESS_ORIGIN missing`.

With harness port 0 the value stays `null`, and `startConductor` derives it per request from the bound harness port. The demo and the tests rely on that.

The origin feeds:
- the panes' `frame-ancestors` and their Referer rule;
- the bridge's `data-harness`;
- the Host allowlist, the API's host:port check (D10), `/api/state` and the startup log;
- the port of the harness mount.

The mount path is the constant `HARNESS_PATH = '/qa'`. There is no `QA_HARNESS_PUBLIC_PORT`, `QA_HARNESS_PUBLIC_PATH` or `cfg.harnessPublic`. When `location.origin` differs from the harness origin, the harness shows a banner linking to it.

**Alternatives.**
- **The exposure plan's `https://w.ts.net/qa`** puts a path in the origin and defaults to port 443.
  - A path breaks CSP source matching, the `postMessage` target and the Referer comparison.
  - On homefree, 443 belongs to prod's Caddy.
- **A comma list of harness origins**, defaulting to both `127.0.0.1` and `localhost`. It covers a mistyped URL by widening the Referer trust and the bridge's targets to every entry.
- **A configurable harness path** can't work: `public/index.html:277` and `public/harness.js:41,265` hard-code `/qa`.

**Why.** One value is the single source of truth for both the URL viewers open and the mount behind it. The spec already makes this argument for the panes.
- 8444 keeps #329's default and stays clear of the pane defaults 8443 and 10000.
- The default is generic. homefree's RC app already serves `https://<host>:8444/`, so at A1 homefree moves its harness to its own port with `QA_HARNESS_ORIGIN=https://<host>:8445` (Q1). The mount follows the origin.
- The loopback default is the URL self-QA (`qa/self.mjs:98`) and agent-identity (`AI/src/serve.ts:72`) already print, so neither needs new config.

### D5. Nested harnesses get `QA_FRAME_ANCESTORS`, which affects CSP only

**Choice.**
- `cfg.frameAncestors` (`QA_FRAME_ANCESTORS`, comma-separated origins) is appended to the pane policy after the harness origin.
- These origins do not pass the Referer rule, and the bridge never posts to them.
- Self-QA gives each inner demo two values: `QA_HARNESS_ORIGIN=<that pane's public origin>` and `QA_FRAME_ANCESTORS=<the outer harness origin>`.
- A tailnet pane origin does not gate the inner demo: it runs with `exposure: 'none'` (D1).

**Alternatives.**
- **Accept blank inner panes in self-QA.** The PR pane is itself a demo harness, and its own panes would not render.
- **A list of harness origins** (rejected in D4).

**Why.** CSP `frame-ancestors` checks every ancestor, not just the parent.
- Inside self-QA, the inner harness is seen at the outer pane's origin (`:3101` or `:3102`), and it sits under the outer harness (`:3100`).
- In the consumer-impact probe in Chromium (`consumer-impact-probe2.mjs`), the inner panes rendered only when both origins were listed.
- 0.2.1 works today only because of its loopback any-port wildcard (`lib/proxy.mjs:72-79`).

### D6. The pane Referer rule stays as #329 wrote it, on http loopback too

**Choice.**
- `paneRefusal(req, harnessOrigin)` is ported verbatim (`F/lib/request-guard.mjs:51-62`): a same-site or cross-site navigation is served only when its Referer's origin is the harness origin.
- Harness responses add `Referrer-Policy: strict-origin-when-cross-origin`, so a stricter browser default can't drop the Referer.
- "Open in new tab" becomes `rel="noopener"`, which keeps the Referer. The GitHub links keep `noreferrer`.

**Alternative.** Trust `Sec-Fetch-Site: same-site`, as 0.2.1's cookie jar effectively does. On ts.net (which is on the Public Suffix List) and on loopback, every other host and port is same-site. That includes the PR pane, which could then frame and drive the base pane.

**Why.**
- Browsers treat `127.0.0.1` and `localhost` as potentially trustworthy, so they send `Sec-Fetch-*` there. Their default referrer policy sends the harness origin as the Referer.
- The Chromium probe confirms it: a pane renders under `http://127.0.0.1:H` with that harness origin, and is refused under `http://localhost:H`.
- Firefox and Safari are unverified; U1's acceptance covers Firefox.
- Side effect: the harness and the panes may now mix `localhost` and `127.0.0.1`. Only the URL the harness itself is opened at must match, and D4's banner says so.

**Constraint on adapters.** An AuthBootstrap landing flow must stay on the pane origin. A step on another site, such as an external identity provider's form, comes back with a non-harness Referer and is refused.

### D7. Pane framing replaces the app's rules; the harness frame lock ships in the same unit

**Choice.**
- **Panes.** Every pane response carries `frame-ancestors 'self' <harnessOrigin> <frameAncestors…>`.
  - `startConductor` wraps each pane as `paneHeaders(gate(createPaneProxy(…)))`. U1 has no gate yet, so there it is `paneHeaders(createPaneProxy(…))`.
  - `paneHeaders` sets the pane policy and `nosniff` before anything else runs, so the identity 403 and the proxy's Host 421 (`misdirected`, `lib/proxy.mjs:53`) carry it too.
  - The proxy's own responses send the merged policy through `writeHead`, which replaces the preset value. Those are proxied responses, the bridge, and the 403, 503 and 502 responses. Node gives `writeHead`'s headers precedence over `setHeader`'s, and a probe on v24.14 confirmed it.
  - The app's own `frame-ancestors` directive is removed from its CSP, and its other directives stay.
  - The app's `X-Frame-Options` is dropped (`F/lib/proxy.mjs:32-42,105-110`).
- **Harness.** Every harness response carries `frame-ancestors 'self'`, `X-Frame-Options: SAMEORIGIN` and the Referrer-Policy (`F/lib/server.mjs:26-29,193-196`).

**Alternatives.**
- **0.2.1 appends its policy next to the app's** (`lib/proxy.mjs:242-246`). An app that sends `frame-ancestors 'none'` or `X-Frame-Options: DENY` still can't be framed. And once the harness frame lock exists, neither can self-QA's panes, which are demo harnesses.
- **Narrowing the claim to proxy-made responses.** It leaves the gate's 403 and the 421 framable by anyone. They show only an error text, but a uniform policy is simpler to state and to test.

**Why.** The proxy decides who may frame a pane. The probe showed that 0.2.1's proxy in front of a frame-locked harness leaves the pane blank, so both changes land together in U1.

### D8. `data-harness` replaces the `#qa=` fragment

**Choice.**
- The proxy puts the harness origin, escaped, on the injected script tag.
- `public/bridge.js` reads `document.currentScript.dataset.harness`. It posts only to `window.parent` at that origin, and accepts replays only from `window.parent` at that origin.
- Delete:
  - `withQaFragment` (`public/harness.js:24-36,311-312`);
  - `harnessOriginFromHash` and the sessionStorage fallback (`public/bridge.js:120-170`);
  - the README contract (`README.md:89`).
- Keep 0.2.1's try/catch around `postMessage`.
- `createPaneProxy` takes `harnessOrigin` as a string or as a function resolved per request.

**Alternative.** Keep `#qa=`. Anyone who frames or opens a pane chooses its fragment. With 0.2.1's wide `frame-ancestors`, the PR pane could frame the base pane with `#qa=<its own origin>` and drive it. The fragment also edits app URLs: `#key=K` becomes `#key=K&qa=…`.

**Why.** The origin should come from the conductor, not from whoever loads the pane.

### D9. The SameSite jar goes

**Choice.** Remove `isCrossSite`, `jarFor` and `parseSetCookie`'s `sameSite` field (`lib/proxy.mjs:58-68,81-125`). Every request the guards admit gets the whole jar, as in #329.

**Alternatives.**
- Keep the jar beside `paneRefusal` (the Part B reader's recommendation).
- Keep it, but bypass it for requests admitted through the harness Referer (the consumer-impact reader's).

**Why.** After `paneRefusal`, the only requests `jarFor` still filters are cross-site navigations admitted through the harness Referer. That means the harness's own iframe loads when the harness and the panes are on different sites, and filtering them signs the pane out. Every other admitted request already gets the whole jar:
- same-origin requests;
- `Sec-Fetch-Site: none`;
- same-site requests from the harness;
- non-browser clients.

### D10. Guards, names and order

**Choice.**
- **API guard.** The harness applies two checks to every `/api/*` request, including reads and the progress stream:
  - **Same-origin.** 0.2.1's private `isSameOriginWrite` (`lib/server.mjs:36-43`), renamed `isSameOriginRequest` because it now checks reads.
  - **Host:port.** `isHarnessHost(headers, harnessOrigin)` refuses a browser request (one with `Sec-Fetch-Site` or `Origin`) whose `Host` is not the harness origin's `host[:port]`.
    - Loopback Hosts and non-browser clients are exempt. So is a `null` harness origin, which logs its own startup error.
    - The exemption for loopback Hosts covers three cases: the `localhost` banner needs `/api/state`; a port-0 harness derives its origin per request; and the outer pane proxy forwards a nested demo's requests with a loopback Host (`lib/proxy.mjs:146` drops the client's).
    - A stale serve handler on another port (D11) then can't hand the harness API to the pages that share its origin.
    - tailscale serve forwards the client's `Host` to a TCP backend: `r.Out.Host = r.In.Host` in `ipn/ipnlocal/serve.go` on tailscale main. U4 confirms this on 1.98.5. If serve rewrote it, the check would see only loopback Hosts there, so it would do nothing, but it would never refuse wrongly.
- **Host allowlist.** It stays on all three servers, and adds the harness origin's hostname.
- **Identity gate.** It wraps whole server handlers, `identityGate(handler, allowedLogins)`, which is #329's shape (`F/lib/server.mjs:198,293-296`). The exposure plan's `authorize` option on `createPaneProxy` (Task 6) is not used.
- **Names and strings.** `lib/identity.mjs` keeps #329's names (`normalizeLogins`, `refusalReason`, `isAllowed`, `identityGate`), and both modules keep #329's refusal strings, which homefree's `access-guard.test.mjs` asserts:
  - `no Tailscale identity: …`
  - `<login> is not in QA_ALLOWED_LOGINS`
  - `cross-site request refused`
  - `cross-site framing refused`
  - `cross-site navigation refused`

  The host:port check adds one new string, `not the harness origin`. The harness shows it in the PR list's load error.
- **Exports.** `./identity` is exported. `lib/request-guard.mjs` is internal: it is tested directly and through the servers.

Order once U2 lands:

| Server | Order |
|---|---|
| harness | frame headers set → identity 403 (tailscale) → Host 421 → bad target 400 → API guard 403 (`/api/*`: another page, or a browser at another host:port) → shutdown 503 (writes) → JSON 415 → route |
| each pane | pane frame policy set → identity 403 (tailscale) → Host 421 → `paneRefusal` 403 → bridge route → `onActivity` → 503 / upstream / 502 |

On the pane path, `tailscale-*` request headers are stripped before the upstream. On the way back, the app's CSP loses its `frame-ancestors`, gets the pane policy, and loses `X-Frame-Options`.

**Alternative.** Host before identity (the delta reader's order). It is just as safe, but the gate would have to move inside each handler.

**Why.** Each guard stops something the others don't.
- A DNS-rebound page is same-origin as far as the browser knows. Only the Host check stops it, plus the missing identity in tailscale mode.
- A page served at another port of the harness's hostname, through a stale or foreign serve handler that reaches the harness, is same-origin with that handler. Only the host:port check stops it.
- The identity gate says which device a request came from. The API guard and the pane guard say which page.
- Wrapping whole handlers means no route, present or future, runs for an unidentified request.

### D11. The reconcile loop

**Choice.** With an adapter:
- `startConductor` reconciles once all three servers are listening, so the targets use the bound ports.
- After that, it reconciles every `cfg.exposureIntervalMinutes` (`QA_EXPOSURE_INTERVAL_MINUTES`, default 5, at most 35791) on an `unref()`ed timer.
- Passes are single-flight, so a hung CLI never stacks processes.
- Once `shutdown()` begins, passes are skipped.
- `mountsFor` is evaluated on every pass, because pane origins may be assigned after start.
- `stop()` and `shutdown()` clear the timer.
- `shutdown()` does not wait for an in-flight pass, and nothing ever removes mounts. After a stop, serve answers 502 until the next start.
- Results are logged only when they change.
- The config stays flat (`cfg.exposure`, `cfg.exposureIntervalMinutes`), as the spec names it.

**Stale handlers.** Since nothing removes mounts, a changed origin or port leaves the old handler serving the old URL.
- The README and the CHANGELOG say so. The operator removes the old handler with `tailscale serve --https=<old port> [--set-path=<path>] off`.
- Until then, D10's host:port check keeps the harness API closed to browsers there.
- Removing handlers automatically would mean recording what the conductor once mounted, and it would risk deleting a handler some other tool owns. The adapter never touches an undeclared `(port, path)`.

**Alternative.** The exposure plan nests the config as `cfg.exposure = { mode, intervalMinutes }`, and reconciles before the servers listen. That points mounts at a backend that isn't up, and gives tests on port 0 meaningless targets.

**Why.** The loop must never block a boot, never crash the conductor and never stack CLI processes.

### D12. The CLI is an exported function plus a thin bin

**Choice.**
- `runExpose({ cfg, exposure, checkOnly, log }) → Promise<0|1|2>` lives in `lib/exposure.mjs`.
- `bin/qa-conductor-expose.mjs` parses `[--check] [--env FILE] [--config MODULE[#export]] [--tailscale BIN] [--socket PATH] [--help|-h]`.
  - It loads `cfg` through `loadConfig`, or through the consumer's loader given by `--config`.
  - It builds the tailscale adapter.
  - It sets the exit code: 0 ok or `--help`, 1 drift or an adapter error, 2 a usage or config error.
- `--config` lets an operator run the bin inside homefree's conductor container with `loadHomefreeConfig`, so homefree needs no wrapper script.
- The bin is an operator and debug tool: `--check` to see drift, and a plain run to ensure the mounts on demand. No deploy runs it (D14).
- The bin reads the conductor's own `.env.qa`, so the GitHub keys `loadConfig` requires are there, even though exposure ignores them. `loadConfig` can't waive core keys (`test/config.test.mjs:76`), and a second, partial loader would drift from the conductor's.

**Alternatives.**
- **A homefree-only `expose.mjs`** (exposure plan Task 8).
- **A bin that only uses the core `loadConfig`.** It fails on any `.env.qa` that relies on a platform's `defaults`; homefree's has no `QA_REPO`, for example.

**Why.** The conductor's loop and the CLI share one code path (`mountsFor` plus `reconcileExposure`), and `lib/exposure.mjs` stays free of `child_process`.

### D13. Versioning and publishing

**Choice.**
- Release as 0.3.0. In 0.x, a minor version may break.
- One tag after the last unit. 0.3.0 is the first version on npm, as `@critical-labs/qa-conductor` (Q2).

- **A plain `npm publish` from the workflow or a laptop.** The token is stage-only, so it would be refused, and a staged version gets a maintainer's look before anyone can install it.

**Why.** Consumers pin tags or npm versions, never `main`: agent-identity pins `#v0.2.0`, and homefree will pin an npm version in its image (Q2). So `main` between units affects nobody. Git-tag pins keep working after the publish. U6 lists the breaking changes.

### D14. Deploys never touch the tailnet mounts

**Choice.**
- With an adapter, the conductor's reconcile loop (D11) owns its tailnet mounts: it adds them once the servers listen and restores them on every pass.
- A deploy restarts the conductor and nothing else. It runs no `tailscale serve`, and no `qa-conductor-expose`, not even `--check`.
- The expose CLI (U5) stays an operator and debug tool: `--check` to see drift, and a plain run to ensure the mounts on demand.
- One-time cleanups, such as removing a stale handler after an origin moves (D11), are rollout steps an operator runs once and records in the RUNBOOK. They never live in a deploy script.

**Alternatives.**
- **The spec (§5):** the deploy runs `expose --check`. Right after a restart, the check races the conductor's own startup reconcile and warns when nothing is wrong.
- **The deploy runs `expose` (ensure), non-fatal** (this plan's first draft). It can't race, but it makes two owners for one piece of state, and a deploy failure mode for something the loop restores within a pass anyway.

**Why.** One owner per piece of state. The loop already ensures the mounts at start and every interval, and reports what it saw at `/api/exposure` and in its log, so a deploy step would add a second writer and nothing else. Keeping exposure out of deploys also keeps the deploy script free of tailnet commands that can fail for reasons unrelated to the release.

### Review points not applied as proposed

- **"Missing or unparseable origins count as non-loopback"** applies to the pane origins only. A `null` harness origin adds nothing (D1), for two reasons:

  - Counting it would put every port-0 config in tailscale mode. That includes agent-identity's recommended smoke test (section 4).

**API**

```js
// Mount = { name: 'harness'|'base'|'pr', host, port, path, target }
//   host: the public hostname, new URL(origin).hostname of this mount's public origin.
//         It is not cfg.host (the bind address), which only `target` uses.
// Drift = { mount: Mount, actual: string | null }
// Exposure = { ensure(mounts) -> Promise<{ added: Mount[], ok: Mount[] }>,
//              check(mounts)  -> Promise<{ ok: boolean, drift: Drift[] }> }
export function mountsFor(cfg, { ports = cfg.ports } = {})          // -> Mount[]
export async function reconcileExposure(exposure, mounts, { checkOnly = false, now = Date.now } = {})
//   -> { ok, checkedAt, drift, added, error }, never rejects
export function createTailscaleExposure({ execFileFn, bin = 'tailscale', socket = null, timeoutMs = 30_000 })
```

**`mountsFor`**
- Each mount's `host` and `port` come from its own public origin:
  - `host` is `new URL(origin).hostname`;
  - `port` is `portOf(origin)`.
- The harness mount is `{ name: 'harness', host, port, path: HARNESS_PATH, target }`, from `cfg.harnessOrigin`.
- The base and PR mounts come from `cfg.paneOrigins`, at path `/`.
- `target` is `http://${hostPort(cfg.host ?? '127.0.0.1', ports[name])}`. It uses `cfg.host`, not a literal, so a `::1` bind gets a target something listens on.
- It throws on:
  - no harness origin;
  - a missing or unparseable pane origin;
  - an origin that isn't `https:` (tailscale serve publishes https only);
  - two mounts on one port;
  - a listen port that isn't an integer ≥ 1.

**`reconcileExposure`** runs `ensure` then `check` (or `check` alone with `checkOnly`). An error comes back as `{ ok: false, error }`; it never rejects.

**`createTailscaleExposure`**
- **Every call** is `execFileFn(bin, [...(socket ? [`--socket=${socket}`] : []), ...args], { timeout: timeoutMs })`. `makeExecFileFn` passes the options through to `execFile` (`lib/exec.mjs:13`).
- **`check`:**
  - runs `serve status --json`. Empty output means `{}`; output that isn't JSON rejects.
  - For each mount it requires `TCP[port].HTTPS === true`.
  - It takes the Web key `<mount.host>:<port>`, or else the first key ending in `:<port>`, then reads `Handlers[path].Proxy`.
  - It compares targets with one trailing `/` stripped. A missing or different handler is drift.
- **`ensure`:**
  - runs `check`, then `serve --bg --https=<port> [--set-path=<path>] <target>` for each drifted mount only. `--set-path` is omitted for `/`.
  - It never runs `reset` or `off`.
  - It never touches a handler at an undeclared `(port, path)`, such as homefree RC's `8444 /`.

**Migration notes** (for the CHANGELOG):
1. **Identity gate.** `QA_EXPOSURE` defaults to `tailscale` when any of these isn't loopback: the harness origin, a pane origin, `QA_PUBLIC_HOST`, a `QA_ALLOWED_HOSTS` entry or `QA_BIND_HOST`. The harness and both panes then answer 403 unless `Tailscale-User-Login` is in `QA_ALLOWED_LOGINS`, and `loadConfig` refuses an empty list.
   - Behind another authenticating front door, set `QA_EXPOSURE=none`.
   - Loopback layouts are unaffected.
   - A code-built `cfg` whose non-loopback origins are assigned after start must set `exposure`.
   - With provisioner-process, PR code runs as the same user and can send the header itself. The gate keeps out other devices, not PR code.
2. **Loopback bind.** In tailscale mode, `QA_BIND_HOST` must be loopback, and a non-loopback bind makes tailscale the default. 0.2's advice to set `QA_BIND_HOST=0.0.0.0` for homefree is withdrawn.
3. **Harness origin.** Open the harness at its origin (`QA_HARNESS_ORIGIN`, logged at startup). The panes refuse frames and navigations from anywhere else.
   - Harness and panes may now mix `localhost` and `127.0.0.1`.
   - The three origins must be distinct http(s) origins. `startConductor` refuses a harness origin equal to a pane origin.
4. **Pane framing.** A pane may be framed only by itself, the harness origin and `QA_FRAME_ANCESTORS`. The app's `X-Frame-Options` and its `frame-ancestors` are dropped.
5. **`#qa=` is gone.** Landing URLs reach the pane unchanged, and the bridge reads `data-harness`.
6. **Harness API guard.**
   - `/api/*` refuses other pages' reads and event streams too.
   - A browser that reaches it at a host or port other than the harness origin's is refused. Loopback Hosts are exempt.
   - Non-browser clients are unaffected.
7. **Pane request guard.** A pane refuses:
   - other pages' writes, preflights, CORS reads, WebSockets and subresource loads;
   - navigations from another site that the harness didn't start.

   AuthBootstrap flows must stay on the pane origin.
8. **Harness frame lock.** Harness responses send `frame-ancestors 'self'`, `X-Frame-Options: SAMEORIGIN` and `Referrer-Policy: strict-origin-when-cross-origin`.
9. **Stale serve handlers.** The conductor and the CLI never remove a handler.
   - After you change an origin or a port, remove the old one with `tailscale serve --https=<old port> [--set-path=<path>] off`. Until then it still proxies to the conductor.
   - That includes a harness moved off a port it used to share with another app.
10. **API changes.**
    - `./proxy` no longer exports `frameAncestors` or `isCrossSite`, and gains `panePolicy`.
    - `parseSetCookie` drops `sameSite`.
    - `createPaneProxy` gains `harnessOrigin` and `frameAncestors`.
11. **Additive.**

    - Exports: `./identity`, `./exposure` and `./adapters/exposure-tailscale`.

    - CLI: the `qa-conductor-expose` bin, for operators and debugging; the conductor's loop owns the mounts, so a deploy needn't run it.

## 5. Decided (MC, 2026-10-02)

These were this plan's open questions. MC, the repo owner, decided them on 2026-10-02, and the sections above follow the decisions.

**Q1. The harness gets its own tailnet port at homefree adoption.**
- **The question.** homefree's harness shared `https://<host>:8444` with the RC app. Under 0.3.0's origin-based trust, every page the RC app serves on that origin would count as the harness:
  - it may frame the panes;
  - its navigations pass the Referer rule;
  - its scripts are same-origin with `/qa/api/*`, which can start sessions on prod-cloned data and post verdicts.

  tailscale serve vouches for the operator on each of those requests, so an XSS in the RC app would become control of the harness.
- **Decided.** At A1, homefree moves the harness to its own port: `QA_HARNESS_ORIGIN=https://<host>:8445`, so the harness is `https://<host>:8445/qa/`. Not the RC app's `:8444` origin. The mount follows the origin (D4).
- **The old handler.** The conductor never removes handlers (D11), so the old `8444 /qa` handler would keep proxying to `127.0.0.1:3100`. There, `isSameOriginRequest` would admit RC pages' `/api/*` calls (`Sec-Fetch-Site: same-origin`), and the banner only warns. So:
  - the A1 rollout removes it once, with `tailscale serve --https=8444 --set-path=/qa off` (section 4 step 6), and the RUNBOOK records the step;
  - the README and CHANGELOG say that an origin or port change leaves a stale handler to remove (U3, U6).

  Until it is removed, D10's host:port check refuses browser calls through it, because serve preserves `Host`. U4 verifies that.
- **Where it lands:** D4, section 4 steps 2, 6, 7 and 9.

**Q2. homefree consumes `@critical-labs/qa-conductor` from npm, through its own image.**
- **The question.** The droplet runs the conductor zero-install, off a read-only bind mount of homefree's checkout. The options were:
  - **(a)** vendor the v0.3.0 tree into `packages/qa-conductor`, with a CI check that it matches the tag (this plan's recommendation);
  - **(b)** install the tag in the compose entrypoint, at every start, on the box;
  - **(c)** publish to npm.
- **Decided: (c), and not vendoring.**
  - The package is published to npm, and 0.3.0 is its first npm version. UP makes it publishable, and U6's tag stages it (D13).
  - homefree's CI builds a `homefree-qa-conductor` Docker image from its platform adapters and the npm package, and pushes it to GHCR.
  - The droplet runs that image instead of the bind-mounted source.
- **Why not the others.** A vendored copy is a second tree to keep in step with the tag, which is the drift the frozen copy already showed. An install at start puts a registry fetch, and a failure mode, in every conductor restart. The image is built and tested once in CI, and the droplet pulls a pinned tag, as it already does for the RC app.
- **A stale premise.** The question assumed `critical-labs/qa-conductor` was private, so that an install would need a credential on the box. The repo is public, which provenance also needs.
- **Where it lands:** section 1, D13, UP, U6, and section 4 steps 1, 4 and 5.

**Q3. Deploys never touch the tailnet mounts.**
- **The question.** The spec (§5) has the deploy run `expose --check`, which races the conductor's startup reconcile right after a restart. This plan recommended a non-fatal `expose` (ensure) in the apply script instead.
- **Decided: neither.** Separation of concerns:
  - deploys never touch the tailnet mounts;
  - the conductor's reconcile loop owns them (D11);
  - the expose CLI (U5) stays an operator and debug tool, for `--check` and for an ensure on demand. It is not part of any deploy.
- **Where it lands:** D12, D14, U5, and section 4 steps 3, 5 and 7.
